# Code引き継ぎ：perf1（スマホが熱くなる）

2026-11-24 Chat作成。本人の報告：遊んでいるとスマホがかなり熱くなるようになった（以前はそうでもなかった、という含み）。端末は iPhone 15 Pro・iOS 27.2、ホーム画面に追加したアプリ（PWA）から起動。WebKit 機能フラグ「Prefer Page Rendering Updates near 60fps」はオン（＝60fps付近に抑えられている前提。fps 上限なしは iPhone では主因ではない見込み）。熱くなるのは試合中で、タイトル画面では熱くならない＝試合の描画・HUD・視界・通信の処理が対象。熱くなり始めたのが 11-23 か 11-24 かは本人も分からない。11-23 の反映分（maptile4・slot3/slot4・tune5 の live-20261123-1〜5）と 11-24 の aim1（live-20261124-1→-2）を同列の候補として、タグ間の比較で切り分ける。iPhone は Safari（WebKit）なので、Chrome の模擬に加えて Mac の Safari の Web インスペクタ（iPhone を USB 接続）で計測する手順を本人向けに書いてよい。
不明点は勝手に判断せず本人に確認。範囲外のコード・コメントは変えない。見た目・ゲーム性は変えない（変える必要があれば先に本人へ相談）。

## 進め方
1. 計測を先にやる。推測で直さない
   - 公開タグ同士を比べて悪化した版を特定する（例：live-20261122-2 と live-20261123-1〜5・live-20261124-2）。maptile4（f39963d）、slot3/slot4・tune5、aim1 が候補
   - 指標：1フレームの JS 時間・描画時間・GPU 負荷、テクスチャの総量。Chrome DevTools のモバイル模擬（CPU 4x〜6x スロットリング）で Performance を同じ操作（練習モード 1分）で取る。実機計測が要るなら本人に依頼の手順を書く
2. 原因を絞ってから最小限の変更で直す

## Chat がコードを読んで付けた当たり（未検証）
- フレームレート上限なし：Phaser.Game の設定に fps がなく rAF 任せ。120Hz で回っていれば仕事量が倍（iPhone の Safari は既定で60付近に抑えるので、実機の fps を見てから判断。Android の 120Hz 機では効く）。上限を付ける場合はゲームの動き（サーバー権威・補間）に影響しないか確認
- 視界：visPoly がレイ360本／視点を、位置が1px でも変わると毎フレーム計算し直す（キャッシュのキーが座標そのもの）。視界はチームで共有なので味方・アシストの数だけ回る。fog は geometry mask（ステンシル）で毎フレーム複雑な多角形
- マップ：mapTex はマップ全体の大きな canvas テクスチャ（MAP.width*T × MAP.height*T）。壁が壊れるたびに mapTex.refresh() で全体を GPU へ再転送（マップチップ化 maptile4 以降に重くなった可能性）。モバイルのテクスチャ上限・メモリも確認
- 毎フレーム Graphics の clear→描き直しが複数（feet・fxG・g・visG・ui）。スロットのモダン演出（slot_modern_fx）や DOM（innerHTML・textContent の書き換え 42 箇所）が毎フレーム走っていないか
- 試合外（待機画面・結果画面・タブが裏）でも描画が回り続けていないか
- HUD の DOM を毎フレーム触っている（main.ts 1561行〜）：$()（hudEl.querySelector）を毎フレーム数十回、style.width・display・borderColor の代入、`.skill i` の `--p`（CT の扇）を毎フレーム更新。WebKit では CSS 変数・conic-gradient の更新が毎フレームの再描画（ペイント）になりやすい。要素の参照は一度だけ取る、値が変わった時だけ書く、で減るか計測
- CSS の filter・box-shadow・blur が 6 箇所。毎フレーム書き換わる要素に掛かっていると合成・ペイントが重い
- 既存の計測フック：URL に ?perf=1 で window.perf に視界の計算時間・フレーム時間が溜まる。実機計測に使う

## 2026-11-24 13時 外部エージェント（Muse）の調査結果（本人が外出中に別環境で実施。この結果を前提に進めてよい）
- 計測：ヘッドレス Chromium・CPU 4x・Bot 通常試合60秒、Math.random を固定シードに差し替えて全版統一、コミット単位で二分。指標は ?perf=1 の perf.ray（視界計算）。フレーム全体の平均には再現性のある悪化は出ず、GPU・テクスチャは未計測
- 原因：maptile3（c5b8c61）で、視界の壁判定の述語が '#' の1文字比較から、'#' のたびに seeThrough の Set 参照（乗算＋Set引き）をする形になった。味方の目×360レイ×タイル走査で1フレーム数万回呼ばれ、perf.ray 平均が 2.34〜2.54ms → 3.51〜3.63ms（+約45%）
- Muse の修正（Muse 側のローカルブランチ perf-fix-visgrid・c5f2aff、未 push。手元にはない）：src/client/main.ts のみ +10/−2。壁判定の結果を Uint8Array に事前計算し、wallVer が変わる時（試合リセット・壁破壊）だけ再構築。レイ走査・ポリゴン生成は不変。修正後 perf.ray 2.59 / 2.50ms。視界ポリゴンは修正前と完全一致を確認
- Muse の環境では e2e が未修正版でも不安定で全 PASS にならなかった

## 方針（上の結果を受けて）
1. Muse の差分を docs/handoff/perf-fix-visgrid.patch に置いた（ベース ac6311f、今の main に `git apply --check` 通過済み、src/client/main.ts のみ +10/−2）。`git apply` で当て、通常の作者でコミットする（git am は作者が perf@localhost になるので使わない）。パッチファイル自体はコミットしない。Chat が読んだ範囲では seeThrough は静的（shared/config.ts の SEE_THROUGH）、tiles を変える箇所はすべて wallVer++ を伴うので、事前計算の作り直しの条件は足りている。念のため tiles を書き換えて wallVer を増やさない箇所がないか grep で確認
2. この Mac で修正前後の perf.ray を同条件で比べ、e2e を通す
3. 視界の修正だけで iPhone の発熱が収まるかは未確定（1フレーム約1ms・GPU 未計測）。反映後に本人が実機で確認し、収まらなければ GPU 側（maptile4 のマップ全体テクスチャ・重ね塗り）を実機計測する。この引き継ぎではそこまでやらない

## 2026-11-24 14時 Muse の描画側計測（追加の原因。これも直す）
- 計測：同じハーネスで WebGL 呼び出しをフック。drawcall は全版で悪化なし（平均11〜14回）
- 原因：maptile4（f39963d）。壁破壊の反映（main.ts 1270〜1274行付近）で、周り±2マスだけ canvas を描き直した後に this.mapTex.refresh() を呼ぶが、Phaser の CanvasTexture.refresh() は canvas 全量（3104×2016×4＝約25MB）を毎回 GPU へ再転送する。壁破壊を含むスナップショットのたびに発火し、60秒で 336MB〜1GB（maptile4 前は約2MB）。1フレーム20MB超の転送が60秒で21回（前は0回）
- テクスチャ総量も 16.4MB→40.3MB（406〜407行の createCanvas('map', 3104, 2016) の1枚）

## 方針（描画側）
4. 壁破壊時の転送を、変わった範囲だけにする。案：描画用の大きな canvas（今の paintMap の描き先）はそのまま GPU に載せない作業用として残し、画面にはマップを一定サイズ（例 512×512）の区画ごとの CanvasTexture／Image に分けて表示。壁破壊時は paintMap で作業用 canvas の周り±2マスを描き直し、その範囲に掛かる区画だけ drawImage で写して refresh する。区画の境目で見た目（オートタイル・壁の正面）が変わらないこと。ほかに Phaser で部分転送できる確実な方法があればそれでもよい（採った方式と理由を報告）
   - 試合リセット（resetMatch）・初回描画は全区画を作り直してよい
   - 見た目は1ピクセルも変えない：修正前後で壁破壊前・後のスクショを比べる
   - 成功基準：壁破壊1回あたりの転送が区画数×区画サイズ程度（512×512なら1区画約1MB）に収まる。drawcall の増加は区画数ぶんまでに留め、報告する
5. 視界の修正（パッチ）と描画の修正は別コミットにする
