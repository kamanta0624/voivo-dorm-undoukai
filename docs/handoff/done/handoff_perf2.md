# Code引き継ぎ：perf2（悪化前との差分の内訳を明確にする）

2026-11-24 Chat作成。perf1 反映後も、悪化前（live-20261122-2）より GPU 転送が 20〜50倍（45〜60秒で 20〜80MB vs 約1〜2MB）、drawcall +2、視界計算 +約0.15ms が残る。本人は差分の中身を明確にしたい。
今回は計測と報告だけ。修正はしない（直し方の案は出す）。不明点は勝手に判断せず本人に確認。

## やること
同じハーネス・同じ条件（perf1 と同じ：ヘッドレス Chrome・CPU 4x・Bot 入り試合・同じ操作、各2回）で、悪化前（live-20261122-2）と今の main を比べ、差を「どこから来たか」まで分解する。

1. GPU 転送の内訳
   - texImage2D・texSubImage2D をフックし、テクスチャ（Phaser のキー）ごと・呼び出し元（スタックの先頭のゲーム側の関数）ごとに、回数とバイト数を集計
   - 区画の送り直し（mapChunk 等）が何回・何MBか、それ以外（ミニマップ miniTex、文字、立ち絵、エフェクトの canvas など）が何回・何MBか
   - 同じ試合で壁が壊れた回数（サーバーの broken の増え方）と、区画の送り直しの回数・バイト数の対応（1回あたり何区画か）
   - 悪化前はなぜほぼ0だったか（壁破壊がどう描かれていたか）をコードで説明
2. drawcall +2 の内訳（何の描画が増えたか）
3. 視界計算 +約0.15ms の原因（透過壁を壁扱いに戻しても残ると perf1 で確認済み。レイの走査距離・視点の数・キャッシュの当たり率など、悪化前との違いを数で比べる）
4. メモリ（作業用 canvas の約25MB 以外に増えたものがあるか）

## 報告の形
- 指標ごとに「悪化前 → 今」の差と、その差を内訳ごとに分けた表（例：転送 +60MB ＝ 区画 +55MB（壁破壊 N 回×1回 M MB）＋ミニマップ +3MB ＋…）
- 差を悪化前の水準に戻すための案と、それぞれの効果見込み・見た目への影響・手間（例：区画を256pxに、壊れた所だけ小さな画像を重ねる、など）。どれを採るかは本人が決める
