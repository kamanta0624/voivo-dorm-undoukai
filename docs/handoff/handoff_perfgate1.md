## 作るもの
### 1. 負荷の検証（verify/perfgate.ts。1回3分以内）
- 決まった場面を自動で通して数える：戦闘（立ち止まる・歩く）／スロットの回転・リーチ・当選・罰／撃破・被撃破・復帰／バフ・デバフ中・パワーアップ中／決着〜結果画面／連戦3試合目（増え続けないか）。場面の作り方は Code が決める（e2e の部屋と E2E_HOOKS、または夜間に作った記録・再生 verify/_replay.ts。通信の形式が変わっても作り直しが楽な方）
- Chromium と WebKit の両方（Playwright）。画面はスマホ（852×393 DPR3、余白に立ち絵が出る縦横比）
- 数えるもの（時間でなく回数を主にする。回数は環境でぶれにくい）：
  - 要素ごとの DOM の書き換え回数／秒（属性・子・文字）。**半分以上のフレームで書き換えられている要素**の一覧
  - 強制レイアウトの回数（DOM を書いた後の getBoundingClientRect・offsetWidth/Height などの読み取り）
  - スタイル再計算・レイアウト・ペイントの回数／秒（Chromium は CDP。WebKit は取れる範囲）
  - 合成の層の数と大きさ、全画面ぶんの層の数
  - WebGL の drawcall・テクスチャの転送量（今の ?perf=1 と同じ）
  - 参考値として1フレームの処理時間（基準には使わない。ぶれるため）
- 超えた時は、**どの要素を・どの関数が**書いているかまで出す（上位の犯人について、書き込みの呼び出し元を記録する。計測の時だけ有効）

- 絶対の決まり（常に不合格）：下の「不要な書き換えの定義」の4つのどれかに当たる／試合を重ねると層・テクスチャ・DOM の要素数が増え続ける

## 本人の追記（2026-11-28 11:08）：合否は「不要な DOM の書き換えがあるか」で決める
- スマホの発熱は本人が実機で定性的に確かめる。検証の役目はそこではない。発熱との対応づけ・代わりの物差しという考え方は捨てる
- 不要な DOM の書き換えがあるかないかは数で決まる。合否はこれで付ける。上の「数えるもの」のうち合否に使うのは次の4つ（ほかは報告用の参考値）

| 不要な書き換えの定義 | 数え方 | 合格 |
|---|---|---|
| 同じ値の書き込み | 書く前と後で値が同じ（文字・属性・style・innerHTML） | 0回 |
| 強制レイアウト | そのフレームで DOM を書いた後に、位置・大きさを読んだ | 0回 |
| 表示が変わっていないのにレイアウトを起こす書き込み | 文字・クラス・innerHTML・transform と opacity 以外の style を、1要素あたり毎秒 N 回を超えて書く（N は表示の値が実際に変わる回数の上限。残り秒なら毎秒1回。案を出す） | 0要素 |
| 動きのための書き込みがレイアウトを起こす | 回転・点滅・追従など毎フレーム動かす物は transform・opacity だけ。それ以外で動かしている要素 | 0要素 |

- どうしても必要な例外は verify/perf_budget.json に要素・理由・上限つきで1件ずつ書く（足すのは本人の了承がある時だけ）
- 「基準値＋余裕」で合否を付けるのは、参考値（層の数・drawcall・転送量・連戦での増え方）だけにする
- night-1128／night-1128b は取り込みの時に検証を通す
